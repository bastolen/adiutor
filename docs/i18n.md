# Languages

How Adiutor speaks English (US), Dutch and Spanish: choosing a language, the translation
catalogues, writing messages, formatting, the checks and adding a language. Back to the
[documentation](README.md). Why it works this way is in
[decision 0014](decisions/0014-languages-without-urls-with-next-intl.md), and why signing in never
saves a language in [decision 0020](decisions/0020-save-a-language-only-when-its-owner-picks-it.md).

## The languages

| Locale  | Language     | Notes                                                     |
| ------- | ------------ | --------------------------------------------------------- |
| `en-US` | English (US) | The default, and the source every translation starts from |
| `nl-NL` | Dutch        | Informal (_je_)                                           |
| `es-ES` | Spanish      | Informal (_tú_)                                           |

They're listed once, in `LOCALES` (`src/lib/i18n/locales.ts`). Only the text changes: URLs are the
same in every language, with no `/nl/...` prefixes.

## How the language is chosen

The language of a request is, in order:

1. the language of the `adiutor.locale` cookie: signed in, the account's own choice, which the
   cookie mirrors; signed out, what was last picked in this browser;
2. Adiutor's default language (`staff_settings.default_locale`), which a staff Admin chooses at
   setup and can change on the staff page;
3. before setup, when there's no default yet, the best match for what the browser asks for
   (`Accept-Language`: `nl-BE` gets Dutch, `es-MX` Spanish, `en-GB` English);
4. English (US).

`resolveLocale` in `src/lib/i18n/resolve-locale.ts` is that rule; `requestLocale()` applies it in
Server Components and actions, and `localeFromHeaders()` (`src/lib/i18n/default-locale.ts`) where
there's only a request's headers (Better Auth's hooks and callbacks).

Adiutor's default comes before the browser's language on purpose: the staff choose the language
their users work in, and anyone who prefers another picks it once, signed in, which saves it with
their account. Changing the default
changes nothing for people who chose a language; it applies to everyone on **Default**, and to
their emails (see [Email](email.md#which-language)).

**Default** is a language choice of its own (`FOLLOW_DEFAULT`, the value `'default'`, in
`src/lib/i18n/locales.ts`): follow Adiutor's default language, now and after a staff Admin changes
it. An account on Default has no saved language (`user.locale` is `null`), and a browser on Default
has no language cookie. Everyone starts on it: new, invited and registered accounts, and the first
Admin when they set up in the default language they chose (otherwise they keep the language they
set up in).

Rendering reads the cookie first. Only without one (signed out on a first visit, or on Default)
does it read the default language: one row, at most once per request (`loadDefaultLocale`, cached
with React's `cache`). Reading the cookie costs nothing extra: every page already renders per
request for the Content Security Policy's nonce
([decision 0006](decisions/0006-nonce-based-content-security-policy.md)).

The cookie mirrors the account:

- **Signed out**, the theme and language button in the bottom-right corner (`PreferencesMenu`, on
  the pages with `AuthLayout` or `CenteredLayout`) sets the cookie (`setLanguageAction`) and reloads
  the page in the new language. Its first language item, **Default**, deletes the cookie; it's
  ticked while the browser has none (the menu reads `document.cookie` when it opens). That choice
  is the browser's only: it's never saved with an account.
- **At sign-in**, the browser gets the account's language: the cookie is set to the saved language
  (`user.locale`), so every browser shows it, and for an account on Default the cookie is removed,
  so the browser follows Adiutor's default language (`rememberLanguage` in
  `src/server/auth/auth-events/language.ts`). Signing in never saves a language: a cookie left in
  the browser says nothing about who picked it, so the next person on a shared browser would get
  the last one's language, for their screens and their emails
  ([decision 0020](decisions/0020-save-a-language-only-when-its-owner-picks-it.md)). It runs once
  the session is settled, so a password whose code step is still to come changes nothing.
- **On the account page**, the Language card (Default first, described with the language it
  stands for now, then the languages) saves the choice with the account (`setOwnLocale`) and in the
  cookie, or, for Default, saves none and deletes the cookie. It then reloads the page, which says
  it's saved (`loadFresh` in `src/components/ui/load-fresh.ts`): a soft refresh would leave pages
  kept alive in `<Activity>` in the old language.
- **Signed in, on a page with that corner button** (the step-up page, an invitation or invite
  link, the not-found and error pages), choosing a language there saves it with the account too,
  as the Language card does (`setLanguageAction` calls `setOwnLocale`; Default saves none), so the
  screens, the card and the emails agree. Two sessions don't save: while a staff member is signed
  in as the user it's refused, like every change, and a session that still has to be confirmed
  with its second step (`mustStepUp`) may change nothing in the account, so its choice stays in the
  cookie, as when signed out.
- **Signing out keeps the cookie**, like the "Last used" sign-in method: it says nothing about who
  signed in, and the sign-in page stays in the browser's language. The next sign-in gives the
  browser that account's language, or removes the cookie for an account on Default.

A second browser that's still signed in keeps its cookie until it next signs in. The cookie isn't
`HttpOnly`, because the last-resort error page reads it in the browser; it holds only a locale,
checked wherever it's read (`localeCookieOptions` in `src/lib/i18n/locale-cookie.ts` sets it). That
page renders without the server, so it can't read Adiutor's default language: without a cookie it
follows the browser's languages, then English (US).

Every language choice (the theme and language menu, the Language card, Email language, Default
language) names each language in itself, next to its flag (`LanguageFlag` in
`src/components/language/language-flag.tsx`, drawn there so the browser gets only these few flags;
`LANGUAGE_OPTIONS` for selects). The flag is decorative and hidden from screen readers: the name
says which language it is, and carries that language's `lang`, in the menu, in a select's list and
in the closed select (`SelectOption`'s `lang`), so a screen reader says "Nederlands" in Dutch
whatever language the page is in. The Default choice has a globe in the flags' place
(`FollowDefaultIcon`); in selects it comes first, with a description naming the language it stands
for now (`useLanguageChoiceOptions`).

Forms that email someone who has never chosen a language (the invite form, Add user, Add company)
have an **Email language** select (`EmailLanguageField`); what it starts on is under
[Which language](email.md#which-language) in Email.

## Server and client components

next-intl ([next-intl.dev](https://next-intl.dev)) does the work, set up without locale routing:

- `src/lib/i18n/request.ts` is its configuration for each request (loaded by the plugin in
  `next.config.ts`): the request's language, its messages, and `timeZone: 'UTC'`.
- Server Components translate with `useTranslations('namespace')` (or `getTranslations` when they're
  `async`), as do server actions and `generateMetadata`.
- Client components use `useTranslations` too. Their messages come from a provider: the root layout
  passes `common` to every page, and `ClientMessages` (`src/lib/i18n/client-messages.tsx`) passes a
  page's own namespaces, around the smallest part that needs them, inside the page's `<Suspense>`.
  An inner provider replaces an outer one's messages, so `ClientMessages` always adds `common`. The
  browser gets only the text the page uses: a namespace (`people`), or just the group inside one
  that the client components use (`admin.staff.name` for the staff name form), which keeps its
  place so `useTranslations('admin.staff.name')` finds it.
- Text in a route's static shell (outside its `<Suspense>`: loading placeholders, the skip link,
  the logo link) comes from small client components that read the root provider (`LoadingStatus`,
  `SkipLink`, `HomeLink`), so Partial Prefetching can prefetch the shell without reading the request.
- Code outside React and outside a Next.js request (emails, services, background jobs, scripts) uses
  `translator(locale, 'namespace')` from `src/lib/i18n/translator.ts`, with the locale it was given.
  `next-intl/server` stays out of `src/server/`.
- `<html lang>` is the request's locale. The last-resort `global-error.tsx` can't ask the server,
  so it bundles `common` in every language, renders in English (US) and switches to the cookie's
  language after mount.
- Page titles are a message each; the root layout's template adds the product name
  (`common.documentTitle`, "{page} · Adiutor"). How pages that need a permission set theirs is
  under Page titles in [Design](design.md#design-and-accessibility).

TypeScript checks every key against the English (US) catalogues (`src/lib/i18n/app-config.ts`), so
a key that isn't there fails `pnpm typecheck`.

A missing message is a bug: outside production it throws, so tests fail on it, and in production
it's logged with the `[i18n]` prefix (the end-to-end tests fail on that console line too) and the
English text shows instead (`messagesFor` lays each language over English).

## The catalogues

One JSON file per area and language, in `src/messages/<locale>/<area>.json`. Each file's top-level
key is its namespace, so `common.json` holds `{ "common": { ... } }`. `src/lib/i18n/messages.ts`
merges them per language.

| Namespace    | What it holds                                                                                                                                                                                 |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `common`     | Shared UI: buttons, dialogs, toasts, pagination, the sort menu, error pages, and the parts other areas use or that sit in a static shell (the code field, the brand panel, the app's notices) |
| `auth`       | The signed-out pages (sign-in, codes, links, passwords, step-up, invitations, setup, sign-in errors); `auth.codes` has the messages chosen by a code                                          |
| `navigation` | The signed-in app's sidebar, mobile menu and account menu                                                                                                                                     |
| `account`    | The account pages (Profile, Security), their actions' messages and the Recent activity descriptions                                                                                           |
| `tables`     | Sort names, directions and table captions                                                                                                                                                     |
| `roles`      | Each role's name and description, by role ID                                                                                                                                                  |
| `audit`      | Audit log actions, the more precise descriptions some events get, the filters                                                                                                                 |
| `errors`     | Why a service refused something (`ServiceError`), e.g. a missing permission                                                                                                                   |
| `validation` | Why input isn't valid: the zod schemas' messages, one per field and problem                                                                                                                   |
| `people`     | Invitations, invite links, role selects, devices and activity (`_people`)                                                                                                                     |
| `admin`      | The staff pages: users, staff, companies, the audit log, errors and jobs                                                                                                                      |
| `companies`  | A company's pages: header, title template, its requests page, members, settings                                                                                                               |
| `dashboard`  | The dashboard: greeting, MFA recommendation, provider warning, shortcuts, the user's companies                                                                                                |
| `requests`   | Requests: their statuses, types and priorities, the request page and the sentences of its history (`_requests`, `requests`)                                                                   |
| `emails`     | Every email: subject, text and footer per template, the security notices' kinds                                                                                                               |

JSON can't hold comments, so the catalogues are the one exception to the `@file` rule; this page and
the loader's JSDoc give their context.

### Writing messages

The translator chooses the word order. To keep that possible:

- **One message is one whole sentence.** Never glue translations together with `+` or a template
  literal (ESLint refuses a translation call inside either), and never pass a piece of a sentence as
  an argument.
- **Arguments are named** (`{name}`, `{company}`), so a language can put them anywhere and in any
  order: `Sort {rows}: {sort}` is `Sorteer {rows}: {sort}` in Dutch. `pnpm lint:messages` refuses a
  translation whose argument names differ from English.
- **Numbers and dates** use ICU arguments (`{total, number}`) or arrive formatted (see
  [Formatting](#formatting)).
- **Plurals wrap the whole sentence**, so each language can agree the verb and the subject too:
  `{count, plural, one {# person has} other {# people have}} access.`
- **Choices by ID** use `select` (`{theme, select, light {Light} dark {Dark} other {System}}`) or a
  key per ID (`roles.<role>.label`), so keys stay static. A helper that names something takes the
  translator, `roleOptions(roles, await getTranslations('roles'))`, or returns the key for the
  caller to translate, `t(describeAuditEvent(action, details))` with the `audit` translator.
- **Links and emphasis inside a sentence** are named tags rendered with `t.rich`:
  `Disconnect it on the <link>Security page</link>.` The same goes for an element inside a
  sentence, such as a relative time (`Last active <time></time>`) or text only screen readers hear
  (`<hidden>Last active: </hidden>`). Renderers are defined outside the component (ESLint's
  `react/no-unstable-nested-components`), e.g. `hiddenTag`, `timeTag` and `userLink` (a link to a
  user's page) in `src/app/(app)/_people/rich-tags.tsx`.
- **Text people hear counts too:** `aria-label`, `title`, `alt`, placeholders and screen-reader-only
  text. When a button shows a short label and is named in full ("Previous" and "Previous page"),
  the visible label is `aria-hidden` and the full name sits in `sr-only` text, so it can be worded
  freely in each language.

### Errors from services

Services don't know who reads their errors, so they never translate: a `ServiceError`
(`src/server/errors.ts`) carries a key in the `errors` or `validation` catalogue and the values of
its arguments, `new ServiceError('conflict', 'errors.members.alreadyMember', { company })`. Its
`message` holds just the key, so logs never hold the values (an address, a company's name). A
list of names is passed as an array (`{ companies: ['A', 'B'] }`), never joined in the service:
`errorMessage` joins it with `Intl.ListFormat` in the reader's language ("A and B", "A en B",
"A y B").
`ErrorMessageKey` type-checks the key against the English (US) catalogues, so a template key
(`` `errors.wrongPassword.${purpose}` ``) works when every case has its message.

The zod schemas in `src/lib/validation.ts` do the same: every issue's message is a key in
`validation`, one whole sentence per field and problem ("Use at most {maximum, number} characters
for the company name."), and a limit's number comes from the issue (`minimum`, `maximum`) or a
refinement's `params`. Keys like `CHOOSE_STAFF_ROLE_MESSAGE` serve zod and services alike.

The text is made where the error is shown, in the reader's language:

- `runAction` (server actions) translates a `ServiceError` with `serviceErrorMessage` in the
  request's language (`requestLocale()`), and invalid input with `validationErrorMessage`: the
  first issue's key, or "Check your input." (`validation.checkInput`) when zod worded it itself.
- A page that shows a service error itself uses `serviceErrorMessage(error, await getLocale())`.
- Results that carry errors per item hold the `ServiceError`, not text: a bulk invitation's failed
  address is `{ email, ok: false, error }`, worded by the action.
- Scripts print English (US) (`DEFAULT_LOCALE`), like the rest of their output.

A message used through `translator` in a namespace the unused-key scan doesn't ignore names its
keys in a comment the scan reads, `// i18n-check t('people.inviteResults.status')`
(`src/lib/invite-status.ts`). So does a key the scan can't see otherwise: a page's title passed to
the metadata helpers (`// i18n-check t('admin.users.title')`), or a key a helper translates with a
translator it's given.

### Emails

An email is written in its recipient's language, not the request's: every template takes a
`locale` (`EmailBaseProps`) and translates with `translator(locale, 'emails.<template>')`, so it
renders anywhere, also outside a request. Subject and text come from the same messages, dates are
formatted with `formatDateTime(date, locale)`, the device with `common.device`, role names come from
`roles`, and `<html lang>` is the locale. Which language each email uses (the recipient's saved
`user.locale`, an invitation's `invitation.locale`, the request's, English (US)) is in
[Email](email.md#which-language). ESLint holds `src/emails/` to the same hard-coded text rules as the
UI.

## Formatting

`src/lib/format.ts` formats dates and times in the reader's language: `formatDate`,
`formatDateTime` and `formatRelative`, each taking the locale. Times are shown in UTC and say so
(`TIME_ZONE`), until people can choose a time zone. Numbers are ICU `{n, number}` arguments in the
messages, which next-intl formats.

| Locale  | Date         | Date and time             |
| ------- | ------------ | ------------------------- |
| `en-US` | Oct 23, 2026 | Oct 23, 2026, 2:05 PM UTC |
| `nl-NL` | 23 okt 2026  | 23 okt 2026, 14:05 UTC    |
| `es-ES` | 23 oct 2026  | 23 oct 2026, 14:05 UTC    |

## Checks

- **`pnpm typecheck`:** every key used in code exists in English (US).
- **`pnpm lint:messages`** (part of `pnpm lint`, and run by the pre-commit hook when code or a
  catalogue changes) runs [i18n-check](https://github.com/lingualdev/i18n-check):
  - every Dutch and Spanish catalogue has every English key, and no others;
  - each translation uses the same ICU arguments and tags as English (in any order);
  - no English key is unused, and no key used in code is missing. Namespaces reached only through
    keys built at runtime or a passed-in translator (`tables`, `roles`, `audit`, `auth.codes`,
    `errors`, `validation`, `emails`) are on its ignore list, since the scan can't follow them. A
    `t` from `useTranslations` called with a key built at runtime makes the scan skip its whole
    namespace, so components call `t` with whole keys (`ok ? t('a') : t('b')`, not
    ``t(`${kind}`)``) and leave keys built at runtime to helpers that take a translator.
- **ESLint** refuses hard-coded text in JSX and in text props (`aria-label`, `title`, `label`, ...)
  in `src/app`, `src/components` and `src/emails`, and translations glued together anywhere.
- **Unit tests** render in English (US) without a provider, and can render in another language;
  see Languages in [Testing](testing.md).

## Adding a language

1. Add it to `LOCALES` and `LOCALE_NAMES` in `src/lib/i18n/locales.ts`, and draw its flag in
   `src/components/language/language-flag.tsx` (TypeScript asks for both).
2. Copy `src/messages/en-US/` to `src/messages/<locale>/`, translate every file, and add its imports
   to `src/lib/i18n/messages.ts` and `src/app/global-error.tsx`.
3. Add its column to the [translation rules](#translation-rules), with the form of address.
4. Run `pnpm lint:messages`, `pnpm typecheck` and `pnpm test`, and add the language to the format
   tests (`src/lib/format.test.ts`).
