# Where the code lives

The folders of the repository and what belongs in each. Back to the [documentation](README.md).

- `src/components/`: shared components, one folder per kind:
  - `ui/`: the component library (see
    [Design and accessibility](design.md#components)).
  - `layout/`: the app and auth layouts. A server action only a shared component uses sits next to
    it (`language-action.ts` for the language menu), not in `src/app/`.
  - `auth/`: the pieces the sign-in and account screens share (the code field `CodeField`, the
    recent-confirmation provider, notices).
  - `brand/`: the logo, the providers that hand pages the staff's name and uploaded logo
    (`StaffNameProvider`, `BrandLogoProvider`), and the sign-in providers' icons (`PROVIDER_ICONS`).
  - `email/`: the blocks the email templates are built from (`EmailLayout` and others) and
    `theme.ts`, their inline styles (see [Email](email.md)).
  - `language/`: the language options (`LANGUAGE_OPTIONS`), `LanguageFlag` and the language fields
    of the forms (see [Languages](i18n.md)).
  - `theme/`: the light and dark options, the hook that reads and changes the preference, and the
    mode a staff Admin may keep every page in (`ForcedThemeProvider`, `useForcedTheme`).
- `src/app/`: the routes. Components only one route uses sit next to its page (e.g. the user detail
  page's `*-card.tsx`); what several signed-in pages share is in `src/app/(app)/_people/`, and
  what the request pages share (the list, the board, the badges, the text, the people, the files
  and the picker that attaches them) in `src/app/(app)/_requests/`. Files are uploaded to
  `src/app/api/attachments/` and downloaded from `src/app/attachments/[id]/`. The logo and the
  browser tab icon made from the brand are served to anyone from `src/app/branding/` (`logo/`,
  `icon/`, and `favicon/`, where `/favicon.ico` is rewritten). A
  company's pages, a user's page, Settings, the Logs and the account pages have a `layout.tsx` with their header and tabs (see
  [Design and accessibility](design.md#layout-and-error-pages)).
- `src/db/`: Drizzle schema and client. Every ID is a time-ordered UUIDv7 generated by Postgres (no
  auto-increment), and every foreign key has an index. A text column that only allows certain values
  has a CHECK constraint built from the same list as its type (`oneOf` in
  `src/db/schema/columns.ts`), except audit actions, which grow with almost every feature, and
  Better Auth's generated user table. A yes-or-no column is NOT NULL with a default (in Better
  Auth's tables, `required: true` with a `defaultValue` in `src/lib/auth.ts`), except the two that
  Better Auth's two-step plugin declares. Migrations are in `drizzle/`.
- `src/server/`: services. Each takes an explicit context and checks permissions itself, so it can
  be tested against a real database. The services every topic shares (access and permission checks,
  actor and context, the metadata of pages someone may not see, audit log, recorded errors, rate
  limits, pagination, search, setup, the language an email goes out in) sit at its root;
  the rest are grouped by topic, and each file's tests sit next to it. A module that outgrew one
  file is a folder whose `index.ts` is its public API (see "Modules that outgrow one file" in
  [Code style](code-style.md)):
  - `src/server/auth/`: sign-in, sessions, MFA and the Better Auth reactions, one file per topic
    (security, accounts, trusted devices, failed sign-ins, email links). `auth-events/` holds the
    hooks that run after Better Auth's endpoints and database writes, and `auth-guards/` the checks
    that run before a request. What one hook of a request passes on to the next is the request's
    typed state in `request-state.ts`, each field saying which hook writes and reads it. Better
    Auth itself is configured in `src/lib/auth.ts`, whose hooks call these two folders.
  - `src/server/people/`: users, staff, memberships, invitations, invite links and companies.
    `invitations/` has one file per flow (the shared rules, the lock, creating the record, sending,
    managing, accepting, and revoking when someone loses access), `invite-links/` one for each
    part of an invite link's life (managing links, the usable link, claiming one with its undo,
    joining with one) and `user-admin/` the staff actions on a user (detail, sessions, own
    account, the sole Admin rule).
  - `src/server/requests/`: listing, showing as a board, reading, raising and changing requests
    (see [Requests](requests.md)), with the checks every change shares in `change.ts`, reading one
    request in `detail.ts` (its texts in `detail-texts.ts`, its conversation in `detail-thread.ts`
    and who reads it in `detail-reader.ts`), who is told what happens to one (`tell-people.ts`)
    and what one person's email about it shows (`read-request-update.ts`, made of the shapes in
    `request-update.ts` and read from `request-update-context.ts`), and their attachments:
    uploading, downloading and removing (`attachments.ts`), the check of a file's bytes against
    its type (`attachment-checks.ts`) and sending uploads with a text (`attachment-claims.ts`).
  - `src/server/jobs/`: background jobs (see [Background jobs](jobs.md)): the tick, leases and
    history, with each recurring job in `recurring/` and every job listed in `registry.ts`.
  - `src/server/queue/`: declaring kinds of queued job and adding jobs to the queue (`queueJob`, `queueJobs`),
    apart from `src/server/jobs`, which imports the code it runs: so code anywhere can queue a job.
  - `src/server/settings/`: Adiutor's settings, one row each in the `setting` table
    ([decision 0034](decisions/0034-settings-in-one-key-value-table.md)): `registry.ts` declares
    every setting (key, schema, fallback) and the checks between them, `store.ts` reads and writes
    them. It imports no server-only code: the default language in `src/lib/i18n/` reads it, and
    Better Auth's configuration reads that.
  - `src/server/storage/`: where attached files are kept (see [Attachments](deploying.md#attachments)):
    a driver per storage (`local.ts`, `s3.ts`, `sftp.ts`) behind `FileStorage`, the keys files are
    kept under, the storage files go to now (`activeStorage`), and the Attachments card of Settings
    (`settings.ts`, with the secrets encrypted by `secrets.ts`). Free of `server-only`, since the
    jobs' command imports it.
  - `src/server/smtp/`: the Mail server card of Settings (see [Sending email](deploying.md#sending-email)):
    reading and saving the mail server (`settings.ts`, tried with a test email first) and telling
    every staff Admin of a change (`notice.ts`). Sending itself is `src/lib/email.ts`, which
    reads the saved mail server through `import()`, so `SMTP_URL` alone never loads the settings.
  - `src/server/webhooks/`: webhooks (see [Webhooks](webhooks.md)): managing them (`manage.ts`),
    the guard that keeps them out of Adiutor's own network (`address-guard.ts`), the JSON body and
    the chat message (`formats.ts`), their signature (`signing.ts`) and one attempt to send
    (`send.ts`). What a webhook is told about a request is read in `src/server/requests/`
    (`read-webhook-news.ts`), beside the emails' `readRequestUpdate`. The rules the browser needs too are in
    `src/lib/webhooks.ts`, the tables in `src/db/schema/webhooks.ts`.
  - `src/server/branding/`: the brand (decisions 0049, 0050 and 0052): the colours, the staff's
    name and the logo and icon, read once per request for pages (`page-colours.ts`,
    `page-name.ts`, `page-images.ts`) and per email (`email-brand.ts`); saving the colours
    (`colour-settings.ts`); uploading and removing the logo and an own icon (`brand-images.ts`,
    drawn again as a PNG in `draw-image.tsx`), and the icon made from them (`brand-icon.tsx`). The
    rules the browser needs too are in `src/lib/branding/`, the table in
    `src/db/schema/branding.ts`.
- `src/lib/`: code shared by the server and the browser, with a few server-only exceptions below.
  General helpers (`env`, `format`, `search-params`, `validation`, ...) sit at its root; the rest
  is grouped by topic. `validation.ts` (zod schemas) is for the server; the limits client
  components need (`MIN_PASSWORD_LENGTH`, `PASSKEY_NAME_MAX_LENGTH`, `MAX_BULK_INVITES`,
  `slugify`) are in the zod-free `input-rules.ts` (see "Browser bundle" in
  [Code style](code-style.md)). `form-data.ts` has `field()`, which server actions use to read a
  text field from a form; it isn't in an action file because a `'use server'` file may only export
  async functions. `env-schema.ts` declares every environment variable, validated at startup (see
  `.env.example`). Server-only: `auth.ts` (the Better Auth configuration), `email.ts`, the
  i18n request configuration and the request and default language in `i18n/`, and
  `not-found-metadata.ts`; `src/client-imports.test.ts` keeps them out of the browser.
  - `src/lib/sign-in/`: the auth client (`load-auth-client.ts` loads it when first needed, outside
    the sign-in pages), the URLs of the code and step-up pages, the code check (`verify-code.ts`),
    cookies, endpoints, secrets, OAuth providers, sign-in refusals, tokens, email links and the
    app's Better Auth plugins for the links' Continue (`email-link-plugin.ts`,
    `request-link-plugin.ts`). It
    isn't called `auth/` because `src/lib/auth.ts` is the Better Auth configuration.
  - `src/lib/authz/`: roles, permissions, guards and who may sign in as whom (`impersonation.ts`),
    all pure functions. `mfa/` holds the MFA rules,
    one file per topic (see [MFA](mfa.md)).
  - `src/lib/tables/`: table state, the table definitions and `page-url.ts`, which builds the page
    links from them.
  - `src/lib/i18n/`: the languages and the request's language, the catalogue loader, next-intl's
    request configuration, the translator for code outside React, and the providers that pass
    messages to client components (see [Languages](i18n.md)).
  - `src/lib/request/`: the client IP address, user agent, request info, CSP and pathname header,
    and how a request was sent (a person's click, `persons-click.ts`; a sign-in link page's own
    Continue, `own-page-post.ts`): HTTP requests, not the requests companies raise.
  - `src/lib/requests/`: the requests companies raise (see [Requests](requests.md)): their
    values, the rules of working on one, the board's lanes, their numbers, their text and the kinds
    of file that can be attached (`attachments.ts`), free of zod and server code, so the database schema, the services and client components can all import it.
- `src/emails/`: the email templates (see [Email](email.md)).
- `src/messages/`: the translation catalogues, one folder per language and one JSON file per area
  (see [Languages](i18n.md)).
- `e2e/support/`: what the Playwright specs in `e2e/` share (fixtures, database, seed, outbox, axe,
  TOTP and global setup).
- `tests/`: helpers the test runners share: `auth/` (authenticator-app codes and storing an
  authenticator), `database/` (which database the tests use, and preparing it), `integration/` (the
  integration tests' setup, which points `@/db` at the test database, and helpers), `i18n/`
  (next-intl's stand-ins for unit tests, and rendering in another language), `ui/` (what component
  and action tests share: the kept-alive page, the form data and the confirmation window),
  `http/` (a receiver for webhooks on `127.0.0.1`) and `build/` (whether a local e2e run can
  reuse the last build).
