# Where the code lives

The folders of the repository and what belongs in each. Back to the [documentation](README.md).

- `src/components/ui/`: the component library (see
  [Design and accessibility](design.md#design-and-accessibility)); `src/components/layout/` has the app and
  auth layouts, and `src/components/auth/` the pieces the sign-in and account screens share (the code
  field `CodeField`, the recent-confirmation provider, notices).
- `src/app/`: the routes. Components only one route uses sit next to its page (e.g. the user detail
  page's `*-card.tsx`); what several signed-in pages share is in `src/app/(app)/_people/`. A
  company's pages and the account pages have a `layout.tsx` with their header and tabs (see
  [Design and accessibility](design.md#design-and-accessibility)).
- `src/db/`: Drizzle schema and client. Every ID is a time-ordered UUIDv7 generated by Postgres (no
  auto-increment), and every foreign key has an index. Migrations are in `drizzle/`.
- `src/lib/authz/`: roles, permissions and guards (pure functions). The MFA rules are the
  `mfa/` folder, one file per topic (role requirement, account state, email codes, sign-in changes,
  step-up, sessions, what a user must do first, sign-in methods).
- `src/server/`: services. Each takes an explicit context and checks permissions itself, so it can
  be tested against a real database. The services every topic shares (access and permission checks,
  actor and context, the metadata of pages someone may not see, audit log, recorded errors, rate
  limits, pagination, search, jobs, setup) sit at its root;
  the rest are grouped by topic, and each file's tests sit next to it. A module that outgrew one
  file is a folder whose `index.ts` is its public API (see "Modules that outgrow one file" in
  [Code style](code-style.md)):
  - `src/server/auth/`: sign-in, sessions, MFA and the Better Auth reactions (auth events and guards,
    security, accounts, trusted devices, email links). `auth-events/` holds the hooks after
    Better Auth's endpoints and database writes, one file per kind (provider accounts, re-verify,
    sessions, users, the phases after a request), and `auth-guards/` the checks before a request
    (attempt limits, the sign-in change lock, signed-in requests, the code step, password resets,
    request checks).
  - `src/server/people/`: users, staff, memberships, invitations, invite links and companies.
    `invitations/` has one file per flow: the shared rules, the lock, creating the record, sending,
    managing, accepting, and revoking when someone loses access.
- `src/lib/`: code shared by the server and the browser. General helpers (`env`, `format`,
  `validation`, ...) and `auth.ts` sit at its root; the rest is grouped by topic. `validation.ts`
  (zod schemas) is for the server; the limits client components need (`MIN_PASSWORD_LENGTH`,
  `PASSKEY_NAME_MAX_LENGTH`, `MAX_BULK_INVITES`, `slugify`) are in the zod-free `input-rules.ts`
  (see "Browser bundle" in [Code style](code-style.md)).
  - `src/lib/sign-in/`: the auth client (`load-auth-client.ts` loads it when first needed, outside
    the sign-in pages), the code check (`verify-code.ts`), cookies, endpoints,
    secrets, OAuth providers, sign-in refusals, tokens and email links. It isn't called `auth/` because `src/lib/auth.ts` is the
    Better Auth configuration.
  - `src/lib/tables/`: table state, the table definitions and search parameters.
  - `src/lib/request/`: the client IP address, user agent, request info, CSP and pathname header.
- `src/lib/auth.ts`: Better Auth configuration; its hooks call `src/server/auth/auth-events/` (audit log,
  session MFA level, deactivated accounts, provider MFA, the re-verify check, security emails) and
  `src/server/auth/auth-guards/` (the checks before a request, including the re-verify marker of
  `src/server/auth/reverify-marker.ts`). What one hook of a request passes on to the next is the
  request's typed state in `src/server/auth/request-state.ts`, each field saying which hook writes
  and reads it. `src/lib/sign-in/auth-client.ts` for Client Components.
- `src/lib/env-schema.ts`: every environment variable, validated at startup (see `.env.example`).
- `src/lib/form-data.ts`: `field()`, which server actions use to read a text field from a submitted
  form. It isn't in an action file because a `'use server'` file may only export async functions.
- `src/emails/`: the email templates (see [Email](email.md)).
- `e2e/support/`: what the Playwright specs in `e2e/` share (fixtures, database, seed, outbox, axe,
  TOTP and global setup).
- `tests/`: helpers the test runners share: `database/` (which
  database the tests use, and preparing it), `integration/` (the integration tests' setup and
  helpers) and `build/` (whether a local e2e run can reuse the last build).
