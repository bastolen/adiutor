## How to work on a request

- **Plan first, ask first, in plan mode.** Every task (anything that changes files, runs commands that change state, or takes several steps) goes through the actual plan mode: enter it (`EnterPlanMode`) if the session isn't in it already, investigate read-only, ask all your questions with the question tool, then present the plan with `ExitPlanMode` and change nothing until it's approved. Answers to your questions aren't the go-ahead; approving the plan is. This also applies to a task handed over by another session, and to a new task or a substantial change of plan halfway through; a small correction within an approved plan doesn't need it again. Subagents carry out a step of an approved plan and don't plan again. Small questions, explanations and read-only lookups get a direct answer, without plan mode. Sessions in this project start in plan mode (`.claude/settings.json`) for the same reason.
- **Delegate to cheaper models when it doesn't cost quality.** Hand self-contained subtasks to an agent on a cheaper model: Sonnet for most delegated work (running and reading tests, investigations, mechanical refactors), Haiku only for simple searches and lookups. Keep design, security and anything that needs this conversation's context on the current model: a better result matters more than a cheaper one.

## Product

- Adiutor is a shared service desk, a ticketing system where companies raise requests with the staff and work them through together by commenting, explaining, approving and reporting. Prepaid hours and billing will come later but aren't designed yet; don't mention them in the UI until they are.
- Wording: staff screens talk about "users", "companies" and "staff" (never "clients", "your team" or "organization"); screens for company users talk about "your company" or its name, and about "requests". "Client" is only the name of a company role (Admin, Client, Watcher). Marketing text speaks to companies. Staff have `user.platform_role` (see `src/lib/authz/roles.ts`), and the name users see and Adiutor's default language are settings (`staff.name`, `staff.default_locale`) in the `setting` table, read and written only through `src/server/settings/` (decision 0034: a new setting is an entry in its registry, typed and checked in code). Invitations and invite links without a company are for staff.
- Requests are built (`docs/requests.md`), with their text in Markdown, staff assigned to them, people subscribed to them, internal notes, emails about them to the people on them, and solutions the company approves; attachments aren't. Don't add navigation or pages for features that don't exist; hint at them in descriptions and empty states instead.

## Documentation

- Document all code with JSDoc-style `/** ... */` comments. This includes TypeScript, config files and CSS.
- Every file starts with a `/** @file ... */` block saying what it is for. Every export, component, function, config option and theme token group gets its own `/** */` comment.
- When you change code, update its comments, the README and the matching page in `docs/` in the same change, so documentation never drifts from the code.
- `README.md` is about the product and the project (what Adiutor is, its features, the tech stack, the quick start, contributing, security reporting, the license). Developer detail lives in `docs/`, one page per topic, each listed in `docs/README.md` and the README's Documentation table; add new pages to both.
- A significant decision (architecture, the security model, process) gets a record in `docs/decisions/` (template and index in its `README.md`). Read the record before changing such a decision; a change gets a new record that supersedes the old one.

- Follow the Airbnb style guide, with braces around every `if`, `else` and loop body (ESLint enforces it), and give every `eslint-disable` comment its reason (`-- why`). No `any` and no `!` (check the value, or use `defined()` / `firstRow()` from `src/lib/defined.ts`), and await or handle every promise. Run `pnpm lint:fix` and `pnpm format` after changes, then `pnpm lint`, `pnpm format:check`, `pnpm typecheck` and `pnpm test` must pass.
- Keep `.vscode/extensions.json` and `.vscode/settings.json` in sync with the tooling: when a linter, formatter or framework that has an official VS Code extension is added, removed or reconfigured, update both files (and the "Editor setup" section of `docs/code-style.md`). Keep the debug configurations in `.vscode/launch.json` and the tasks they start in `.vscode/tasks.json` working too: when a script, a test runner's entry point or the dev server's setup changes, update them and "Debugging in VS Code" in `docs/development.md`.

- `pnpm audit` must stay clean (CI runs `pnpm audit --prod`). Fix a new advisory, or, when it can't be reached from the app, add it to `auditConfig.ignoreGhsas` in `pnpm-workspace.yaml` with a comment on why and when it goes away; remove the entry once its fix lands.
- In GitHub workflows, pin every action to a full commit SHA with a `# vX.Y.Z` comment and container images to a digest (Dependabot updates actions, Renovate npm packages and images), and give each workflow the least permissions it needs (`permissions: {}` or read-only at the top).
- Add or update tests with every change: Vitest `*.test.ts(x)` files next to the code in `src/`, Playwright specs in `e2e/`. Tests cover the application only: no tests for config, tooling, scripts or the test helpers in `tests/`.

## UI and accessibility

- The UI must feel premium and trustworthy: calm, consistent, polished in every state. Build it from `src/components/ui/` and extend those components rather than styling one-off elements.
- Target WCAG 2.2 AA. Use the semantic colour tokens from `src/styles/theme.css` (`surface`, `foreground`, `muted-foreground`, `primary`, `danger`, ...); never lighten text with opacity (ESLint enforces it in `src/app` and `src/components`), and check contrast for any new token in both modes.
- Menus, selects and dialogs use Radix UI (via the wrappers in `src/components/ui/`). Destructive actions go through `ConfirmDialog`, never `window.confirm`.
- Everything must work with the keyboard alone: visible focus (`focusRing`), logical tab order, Escape closes the open layer and focus returns to its trigger. When an action removes the control that had focus (a removed row, a swapped button, a dismissed notice), focus moves to its card's heading or the main content (`restoreFocusIfLost` in `src/components/ui/focus-fallback.ts`), never `<body>`. Icon-only buttons need an `aria-label`; decorative icons get `aria-hidden`.
- Give a `Card` an `id` (a section ID, `isSectionId`) when a control in it can send the user away and back (a confirmation, a provider, an emailed link), so they come back to that card: return addresses keep the page, its tables (`PageUrl.current()`) and the card's anchor (`ReturnToField`, `useRecentConfirmation`, `confirmChangeUrlFor`). Never build a return address by string concatenation without encoding it.
- Pages stay alive across navigation (Cache Components keeps them in React `<Activity>`), so forms use `useTransientActionState` (and pass its `onSubmit` with the action, so a refused submit keeps the input; a form that edits a saved setting with a select passes `resetOnSuccess: false`, or the select would jump back to the value from before the save; a text field is reset, so it shows the value as it was saved), and status messages and dialog open state use `useTransientState` (`src/components/ui/use-transient-state.ts`): an error message or an open dialog must not still be there when the user comes back. ESLint refuses `useActionState` outside that file.
- Every change of who the browser acts as (signing in or out, starting or ending a sign-in as a user) ends with a full page load, `loadFresh` (`src/components/ui/load-fresh.ts`), never `router.push`/`router.replace` or a server action's `redirect()`: pages kept alive would still show the previous person's values in their fields. Pass `{ everyTab: true }` once the server has made the change, so the browser's other tabs load their page afresh too (`ReloadWhenActingAsChanges`); the message between tabs never says who. Where the change has to end in a redirect (a form that works before JavaScript loads), the server action calls `markActingAsChanged()` first, which has the page it reaches load afresh in every tab. A toast for the next page goes through `showToastAfterLoad` (`ActionDialog`'s `loadOnSuccess` does both), and a busy button stays busy with state of its own, never a promise that doesn't settle (React would hold up every other transition behind it).
- A text in Markdown is written in `MarkdownField` and shown with `MarkdownText` (`src/components/ui/markdown/`). The field's editor and its libraries load only through the field's `import()`, and the languages of highlighted code only once a text has a block of code; nothing else imports the `editor*` files. Keep the editor in step with the server's rules when either changes (HTML stays text, only whole `http` and `https` addresses link, images never load: `editor-extensions.ts` and `tree.ts` / `elements.tsx`, and for a text in an email `src/components/email/email-markdown.tsx`, which renders the same tree), never let it take Tab or Shift+Tab, and test what it knows of Markdown on an editor without a page; typing in it is for the end-to-end tests (`markdownEditor`).
- Ship only the code a page needs to the browser. Client components never import zod or `@/lib/validation` (shared limits live in `@/lib/input-rules`), pages outside the sign-in pages load the auth client with `loadAuthClient()` when an action needs it, and other libraries needed only for an action are loaded with `import()` when it happens (like `qrcode`). `src/client-imports.test.ts` enforces this; add new heavy libraries to its rules.
- The Content Security Policy only runs scripts with the request's nonce (`src/lib/request/csp.ts`, set by `src/proxy.ts`): never add inline scripts or `on…=` attributes; an unavoidable inline `<script>` takes the nonce from `(await headers()).get(NONCE_HEADER)`. Specs import `test`/`expect` from `e2e/support/test.ts`, which fails on CSP violations the pages report (ESLint enforces it). Keep the proxy matcher (`src/proxy.ts`) from skipping paths by extension: only real static files may skip it.
- Every control needs hover, focus-visible, disabled and busy states and the right cursor (pointer on clickable things, not-allowed when disabled). A control stays focusable while it's busy (`Button`'s `loading`, `SelectField`'s `busy`: `aria-busy` and `aria-disabled`, presses ignored), and a button that its own use makes wait stays focusable while it can't be pressed (`Button`'s `focusableWhenDisabled`, e.g. "Send a new code" counting down): never disable the control that was just used, or keyboard focus is lost. Where several buttons start actions of which one runs at a time, only the pressed one is busy (`whileRunning`). Forms use visible labels and `autocomplete`. In the signed-in app, every success is a toast and every error is shown inline with `Alert` and as a toast (`useToast` in `src/components/ui/toast.tsx`; `RowAction`, `ActionDialog`, `RoleSelect`, `ResultAlert` and `Alert`'s `alsoToast` do it for you). The one exception is an error an open dialog shows: it stays inline, without a toast, because a toast is a layer above the dialog and would take the first Escape (`Modal` marks its content with `InsideDialog`, which `ResultAlert` and `alsoToast` follow; never call `useToast` for an error from inside a dialog). The signed-out pages show results inline only.
- A page may be wider than the app's content only where the room shows more (decision 0042): a request (text to read and write), the boards and the lists of requests, the list of users, and the two sections whose tabs hold such a list: a company's pages (its list and board) and Settings (its staff). Wrap the page in `WidePage` (`src/components/layout/wide-page.tsx`), which grows from 1280px of screen up to 1200px of content and measures the room in the app layout's content column; a section whose tabs hold such a page wraps all of them in its layout (`companies/[companyId]/layout.tsx`, `admin/settings/layout.tsx`), so its header and tabs keep their place from tab to tab. Every other page keeps the usual width: a short table, a form or a page of details gains only empty space.
- Tables of records sort and paginate: define each table in `src/lib/tables/tables.ts` (a page's main table has no prefix; every other table on the page gets its own), read its state with `parseTableState`, build its links with `createPageUrl` (from known parameters only, never by copying the URL) and render `SortMenu` (the only way to sort: headers are plain `Th`s with `aria-sort={table.ariaSort(...)}`) and the pagination as the card's footer (`paginationFooter`). The content stops growing at 1280px, so pick columns that fit 942px there and move the rest under the name; a table on a `WidePage` has 1198px from 1536px of screen (`2xl`), where what sits under the name may get a column of its own (`hidden 2xl:table-cell`, with `2xl:hidden` under the name), like a request's company across companies and a user's companies and MFA, and only a table on a `WidePage` gets `2xl:` columns. Long names and addresses get `wrap-anywhere`. List services take `Partial<TableState>`, resolve it with `resolveTableState` and return `Paged<T>` (via `paginate` in `src/server/pagination.ts`), ending every sort with the row's ID. Pagination e2e tests use only the seeded "Adiutor Tests Paging" company. The board of requests (`/requests/board`, decision 0037) is the one exception: its lanes aren't tables, so they have no pagination footer (an open lane shows the cards per lane chosen with `PageSizeLinks`, a closed one its latest five, and a lane with more links to the list), but they keep the list's sort and its Sort menu.
- Every page must pass `e2e/a11y.spec.ts` (axe, light and dark) and new interactive patterns get a check in `e2e/keyboard.spec.ts`. Add new pages to `a11y.spec.ts`.

## Requests

- Requests live in `src/lib/requests` (values, rules, numbers, text; free of zod and server code), `src/server/requests` (the services) and `src/app/(app)/requests`, with what the pages share in `src/app/(app)/_requests`. `src/lib/request/` is about HTTP requests. How requests work is in `docs/requests.md`; read decision 0019 before changing the model.
- Request types are rows in `request_type` that staff Admins manage (decision 0027): take them from `listRequestTypes` and a request's type name from the services, never from a list in code. A request holds a type's key, which never changes; a picked type goes through `typeToGive` (it must exist and not be archived), and a type is archived, never deleted.
- Who may do what with a request comes from the rules in `src/lib/requests/rules.ts` (`requestSide`, `mayChangeStatus`, `statusChoices`, `statusAfterReply`, `subscriberScope`, `mayProposeSolution`, `mayAnswerSolution`) and the four `requests:*` permissions; never decide it in a page or a component. Waiting for approval (`proposed`) comes only with a reply sent as the solution, and is left only through `answerSolution` (also from the email's Approve and Deny links, `answerByLink`, which answer only on a person's click and only for their person and proposal) or the staff's own changes (decision 0033).
- Company users never see a priority, an internal note, or anything else meant for the staff: the services leave it out for readers without `requests:view-internal` (results, history and the last activity), so filter new staff-only data in the service, never in the page. A kind of entry only the staff see goes in `STAFF_ONLY_ENTRY_KINDS` (`src/lib/requests/values.ts`), which every query of entries for a company reader filters with, and never moves the request's last activity.
- Requests show people by name only (`requestPerson`), never an email address, and the waiting status in the reader's words (`StatusBadge` with their `requestAudience`). A person's ID goes only to readers with `users:view` (the staff), for the link to the user's page; nothing else about who someone is may reach a company user's browser.
- The people on a request are the rows of `request_participant`, each with a role (`assignee` or `subscriber`; read decision 0025 before changing it), so every query on it names the role. Who is subscribed is read with `loadSubscribers` only (the people who can read the request by now), a change that takes someone's access to requests away calls `unsubscribeFrom` after it, in its transaction, and subscribing leaves no entry in the history. Someone at a company sees the subscribers from their own company, never which staff members follow a request. The dialog that changes subscribers names people by their key (`mentionKey`), never a user ID.
- Who is told about what happens to a request is decided in one place, `tellPeopleOnRequest` (`src/server/requests/updates.ts`; read decision 0031 before changing it): the people on the request, never whoever did it, as a `request-update` job per person queued in the change's transaction. What a person's email shows is read when it's sent (`readRequestUpdate`): nothing for someone who is no longer on the request or can't read it, names as the request's page gives them, never an address or an ID, and nothing meant for the staff to a company. A request's text is shown in an email with `EmailMarkdown` only.
- Which webhooks hear of what happens to a request is decided in one place too, `tellWebhooks` (`src/server/requests/tell-webhooks.ts`; read decision 0046 before changing it): a `request-update` job per webhook and piece of news, queued in the change's transaction for the webhooks that are on, chose the event and cover the request's type, whoever made the change. A new kind of entry decides its webhook event in `WEBHOOK_EVENT_OF_ENTRY` (`src/lib/webhooks.ts`). What a webhook is told is read when it's sent (`readWebhookNews`): people by name and side only, never an address, a user ID or who was signed in as whom. A receiver that fails is recorded on its delivery and never throws: only Adiutor's own faults fail the job.
- A mention in a request's text is a marker that points at a row in `request_mention` (`src/lib/requests/mentions.ts`; read decision 0023 before changing it): the stored text never holds a name or a user ID, and a text that's being written holds a key (`mentionKey`), never an ID. A shown mention carries the person's key (`data-mention-key`) only for readers with `requests:contribute`, so the editor reads a pasted mention back (decision 0035); keep the editor's atoms (mentions, images) readable from the HTML they render. Who may be mentioned comes from `listMentionable` only (someone at a company: their colleagues and the staff the request already shows them), and a text's mentions are stored with `storeMentions` in the transaction that stored the text.
- A request's description, replies and internal notes are edited only through `editRequestDescription` and `editReply` (decision 0024: who may edit what is in `rules.ts`, each edit keeps the text it replaced as a `request_text_version` for the staff); nothing else changes a stored text.
- An internal note is a `note` entry (decision 0026), added with `addNote` by the staff who work on requests (`mayWriteNote`) and read by every staff role. A mention in a note never subscribes someone at the company to the request, and nothing that tells people about a request (emails, notifications) may tell someone at the company about a note: a note is emailed only to the staff on the request and the staff it mentions (`tellStaffOnRequest`), and `readRequestUpdate` builds note items only for readers with `requests:view-internal` (decision 0032).
- Show a request's text with `RequestText`, store it with its format marker (`WRITTEN_TEXT_FORMAT` for every new text: Markdown) and clean it with `cleanMultilineText`; never render stored text another way. Markdown is rendered on the server only (`MarkdownText` in `src/components/ui/markdown/`; read decision 0021 before changing it): nothing someone typed becomes HTML, a link other than a whole `http` or `https` address, or an image that loads, and a new kind of element goes through the allow-list (`sanitize.ts`) and gets its own component (`elements.tsx`). Show numbers with `formatRequestNumber` and the saved prefix, and link with `requestPath`. Page titles carry the number, never a request's title.
- Every change to a request goes through `requestToChange`, refuses a deactivated company, takes a rate limit keyed on `actingUserId(actor)` and runs through `changeRequest` (which starts with `assertStillManages`, checks that a sign-in as the actor still holds, and locks the request's row). A new kind of event is a new kind of `request_entry`, with its sentence in the `requests` catalogue. Request work records no audit events: the request's history is the record. The one exception is a change of subscriptions made while signed in as a user, which leaves no history: it goes to the audit log (`request_subscribers_changed`, a `STAFF_ONLY_AUDIT_ACTIONS` action the user's own activity leaves out).
- Request work is the one kind of change a staff member signed in as a user may make (decision 0028): never call `assertNotSignedInAs` in it (managing request types is staff settings, and does), store `signedInAsWork(actor)` with every row that says who did it, and let only the user and `audit:view` staff learn of it (`maySeeSignedInAsWork`, in the service).
- No test changes the seeded requests (`SEEDED_REQUESTS`): a test that changes a request stores its own (`storeRequest`), and never counts rows that other specs can add.

## Languages

- Every text people see or hear (JSX text, `aria-label`, `title`, placeholders, toasts, errors, page titles, emails) is a message in the catalogues `src/messages/<locale>/<area>.json`, added to every language in the same change: en-US is the source, nl-NL and es-ES follow the translation rules in `docs/i18n.md` (informal je and tú, "Adiutor" never translated). `pnpm lint:messages` checks they're complete; ESLint refuses hard-coded text in JSX and text props (`src/app`, `src/components`, `src/emails`).
- One message is one whole sentence with named ICU arguments, so each language chooses its word order: never glue translations together (`+`, template literals) or pass a piece of a sentence as an argument. Plurals wrap the whole sentence; links inside a sentence are `t.rich` tags.
- The language is the person's own (the `adiutor.locale` cookie, mirroring their account) while Adiutor offers it, else Adiutor's default (the `staff.default_locale` setting), else, before setup only, the browser's `Accept-Language`: use `requestLocale()`, `localeFromHeaders()` or `recipientLocale()`, never your own parsing, and check any other stored language with `offeredLocale` (a language that's turned off counts as none). Language choices offer only the languages that are on (`useOfferedLocales`, `useOfferedLanguageOptions`; nothing to choose with one left), name each in itself with its flag (`LANGUAGE_OPTIONS`, `LanguageFlag`), and services refuse a language that's off (`assertLanguageOffered`). Decision 0029.
- Server Components, actions and metadata translate with `useTranslations` / `getTranslations`. Client components get messages from the root provider (`common`) or `ClientMessages` (the page's own namespaces, inside its `<Suspense>`). Code outside React or a Next.js request (emails, services, jobs, scripts) uses `translator(locale, namespace)` with the locale it's given; keep `next-intl/server` out of `src/server/`.
- Text in a route's static shell (outside its `<Suspense>`) comes from a client component that reads the root provider, so Partial Prefetching can prefetch the shell.
- Format dates with `src/lib/format.ts`, the reader's locale and their time zone (`getTimeZone()` / `useReaderTimeZone()`, emails the recipient's, `recipientTimeZone`; times are stored in UTC): pages show a time without its zone, emails and copied text name it (`zoneName`). Numbers are ICU `{n, number}` arguments in the message. A cached function never reads the request's language or zone: pass them in.

## Email

- Every email is a React Email template in `src/emails/` built with `EmailLayout` and the blocks in `src/components/email/` (inline styles from `theme.ts`, no CSS variables). Never send hand-written strings.
- Each template's props extend `EmailBaseProps` and its exported `PreviewProps` start with `...PREVIEW_BASE` (both in `src/emails/base-props.ts`: the app URL `https://adiutor.dev`, `logoSrc: '/static/logo.png'` and `locale: 'en-US'`), followed by Adiutor example data. Each template translates with `translator(locale, 'emails.<name>')` and is written in the recipient's language (`recipientLocale`: their saved `user.locale`, else Adiutor's default language for someone on Default, never the sender's, else en-US; an invitation's `invitation.locale`; see `docs/email.md`), and a time it shows is in the recipient's zone with the zone named (`recipientTimeZone`: their saved zone, else their invitation's sender's, else Adiutor's default). Each template also exports a builder that renders it with `renderEmail`, has a footer `reason`, and is covered in `src/emails/emails.test.tsx` in every language (subject, links, plain text). The main link must be the first link in the plain text.
- Images are linked from the app's public URL, never attached. Templates loaded by `src/lib/auth.ts` are imported inside the send callbacks, so loading the auth config never loads React.

## Authentication and permissions

- Every permission check goes through `src/lib/authz` (pure rules) and `src/server` (services check permissions themselves; pages use `src/server/authz.ts`). Never compare roles inline in pages or components (ESLint catches a role compared with a string).
- Only `src/lib/authz/mfa/` decides MFA rules (who needs it, what counts, which sign-ins had a second step); don't re-implement them elsewhere. They take the user's MFA role (`mfaRoleOf`: staff Admins and Managers, or the Admin of an active company, require MFA), never the staff role alone. `getActor()` sends users whose role requires MFA to the Security page until they have it; only the account pages and the navigation may pass `allowMissingMfa: true`. Load a user's MFA facts with `loadMfaStates` / `loadMfaContext` (`src/server/auth/mfa-state.ts`), which leave out provider accounts linked at sign-in that the user hasn't confirmed (`account.confirmed`), and decide whether a session counts when it's read (`isSessionMfaVerified` with the current MFA role), never from `session.mfa_verified` alone.
- Account existence (whether an email has an account or is a member) may only be shown to staff, via `mayRevealAccountExistence`. Company users' and signed-out screens must give identical responses.
- Never show users the IP address or browser of someone else (an admin who acted on their account, whoever typed a wrong password for their address), on screens or in emails: only staff with `audit:view` see those, in the audit log.
- Pages are protected by default by `src/proxy.ts`; only add a path to `PUBLIC_PATHS` when it must be reachable signed out. The proxy is never the security check.
- Read the signed-in user with `getActor()` / `requireCompanyAccess()` inside a `<Suspense>` boundary (Cache Components).
- OAuth providers are declared once in `src/lib/sign-in/oauth-providers.ts` (`OAUTH_PROVIDERS`, `MFA_PROVIDERS` for those that can prove MFA, and `PROVIDER_ACCOUNT_NAME_CLAIMS` for how their accounts are named, e.g. GitHub's username), with their credentials in `src/lib/sign-in/providers.ts`, their icon in `PROVIDER_ICONS` and their MFA check in `src/server/auth/provider-mfa.ts`. Never compare provider IDs such as `'github'` inline (ESLint flags them outside the files above): use `isMfaProvider`, the configured lists (`availableProviders`, `signInProviders`) and `PROVIDER_LABELS` (the file comment lists what a new provider needs).
- A provider account's name and picture (`account.accountName`, `account.accountImage`) are noted from the provider's profile in Better Auth's `user.validateUserInfo` and stored by the account hooks of the same request (`noteProviderProfile`). That hook must never refuse anyone: Better Auth refuses the sign-in when it throws or returns an error. Account names are personal data: only for display (match accounts by `accountId`), never logged, shown to the user themself and, on the user's page, only to staff Admins (`users:manage`). A picture's provider address never reaches a browser and is never logged: the picture a person shows is served from `/avatars/<account>` (decision 0022), to the readers who see their name.
- Sessions last a fixed 7 days (`disableSessionRefresh` in `src/lib/auth.ts`). Don't turn session refresh back on without refreshing the cookie where cookies can be set (a Route Handler, a server action or the proxy): pages render where they can't, so the database row would outlive the cookie.
- Signing out removes every cookie the browser sends except the "Last used" sign-in method and the language (`cookiesToClearAtSignOut` in `src/lib/sign-in/auth-cookies.ts`), so the next person on the browser starts clean: set new cookies with `path: '/'` so sign-out reaches them, and key anything a user leaves in `localStorage` to that user, or better, save it with their account.
- Changes that would leave a role that requires MFA without it are refused in the guards, the services and the Security page through one rule (`wouldRemoveRequiredMfa`); add new sign-in changes to it (and to `signInChangeOf` for Better Auth endpoints). One sign-in change per user at a time: the guards take the lock for those endpoints, the OAuth callback decides whether a provider counts under it (`holdSignInChangeLock`), and services that change sign-in methods themselves run inside `withSignInChangeLock` (`src/server/auth/sign-in-change-lock.ts`), reading the MFA state only once they hold it. Better Auth's server-only endpoints (e.g. `setPassword`) have no path, so the guards never see them: call them through a service that applies the rules (`setFirstPassword`).
- Changes that can make a user's role require MFA (staff or company roles, memberships, joining, reactivating a company) run inside `withMfaPromotion` (`src/server/auth/mfa-promotion.ts`) in their transaction, so the user's sessions without a strong factor end.
- Staff can sign in as a user (decision 0017, `src/server/auth/impersonation.ts`): the session stays theirs, and `getActor()` returns the user with `signedInAs` set. Every service that changes something calls `assertNotSignedInAs(actor)` first, and server actions that call Better Auth themselves, or send the user to confirm before a service would refuse, call it before that. Only the user's own work is allowed (their request work, and hiding the MFA tip; list it in `OWN_WORK` in the authorization matrix, which refuses every other operation outside `READS` while signed in as someone); such work records the staff member, which only staff with `audit:view` and the user may see.
- Email codes are never accepted once an authenticator app is set up, and never count for roles that require MFA (`allowsEmailCodes`). Changing sign-in methods (passkeys, linked accounts, two-step verification, backup codes, a first password) needs a confirmation with the second step from the last 15 minutes (`mfaConfirmedUntil`) once the account has MFA or any other second step (`canConfirmSessions`); `src/server/auth/auth-guards/` enforces this for Better Auth's endpoints too, and server actions and services check `needsRecentConfirmation(actor)`. The guards' refusal codes are declared once in `src/lib/sign-in/sign-in-refusals.ts`, with their messages in `auth.codes`; forms turn an error into text with `authErrorText`, which shows only the refusals in `SERVER_WORDED_CODES` as the server words them (never Better Auth's English). On the Security page, use `useRecentConfirmation` so starting such a change sends the user to the step-up page first.
- The links in emails about requests sign their recipient in (decision 0036, `src/server/auth/request-links.ts`): a session they start (`fromRequestLink`) skips the step-up page for every role, but never counts as a confirmation (`mfaConfirmedUntil`) or a fresh sign-in (`signedInAtOf`), so keep it unconfirmed in every new step-up rule. They end with the user's trusted devices: forget both through `forgetSecondStepSkips`, never `forgetTrustedDevices` alone.
- Only the Better Auth endpoints the browser uses are open over HTTP (`src/lib/sign-in/auth-endpoints.ts`); when the browser needs another one, move it from `DISABLED_AUTH_PATHS` to `BROWSER_AUTH_PATHS` deliberately.
- Better Auth's errors land on `/sign-in-error` (`onAPIError.errorURL`), which explains them without the code and records a reference for admins with `recordSignInError` (`src/server/auth/sign-in-errors.ts`): the log line holds only the reference and code, and the `sign_in_error` row (kept 7 days) adds Better Auth's description and the user ID. Add a message (`auth.codes`) and its code (`src/app/sign-in-error/messages.ts`) for new codes users can hit.
- Server code never logs personal data or secrets itself (addresses, names, tokens, request bodies): log what failed, with an ID where needed. Logs drop database values through `installLogRedaction` (`src/lib/log-redaction.ts`, installed in `src/instrumentation.ts`, and for scripts by `runScript` in `scripts/run-script.ts`, which every script that uses the database runs through); scripts may still tell the operator what they did, e.g. which address they signed out. The one exception is the development email fallback in `src/lib/email.ts`, which prints whole emails when there's no SMTP server and never runs in production.
- Read the client's IP with `requestInfoFromHeaders` and `ipAddressOptions` (the same resolution Better Auth uses); never parse `X-Forwarded-For` yourself.
- Read the session token from a request only through its signed cookie (`getSignedCookie` with Better Auth's secret, see `signedSessionToken`), never by parsing the cookie: a token from the database must not pass for a session. Don't keep OAuth tokens beyond the request that needs them (`withoutKeptTokens`).
- When someone loses the right to manage a company or the staff (role change, removal, deactivation, deletion), revoke what they sent with `revokeInvitesWithoutManager`.
- Giving someone a lasting way in needs the giver's confirmation with their second step from the last 15 minutes, like changing sign-in methods: any staff role (or a higher one) and a company's Admin role, by invitation, invite link, role change, adding a member, registering a company or reactivating an account that kept such a role (`grantNeedsConfirmation` and `reactivationNeedsConfirmation` in `src/lib/authz/guards.ts`). Services enforce it with `assertConfirmedForGrant` (code `confirmation_required`), actions wrap the service call in `confirmFirstIfNeeded` (to the step-up page and back), and forms ask before anything is typed (`useConfirmBeforeGrant`, `ConfirmFirstNote`, `RoleSelect`'s `target`, `ActionDialog`'s and `RowAction`'s `confirmFirst`). Becoming a staff Admin emails the other staff Admins (`notifyStaffAdminAdded`).
- Nobody raises their own staff role (`isStaffRoleRaise`); they may only step down. Finance and Support can't use invite links (`mayUseInviteLinks`), directly or through the invitation a link sends; check it before a link is used up.
- New permission-relevant services get a row in `src/server/authorization-matrix.int.test.ts`.
- Every security-relevant change (sign-in methods, sessions, roles, accounts, invitations) calls `recordEvent` from `src/server/audit.ts`, in the change's transaction where there is one. Changes the user should know about also queue a security notice (`queueSecurityNotice`, after the change commits); it names the device and IP address only when given the change's audit event (`auditEventId`, which `recordEvent` returns), which is for changes the user made themselves. Only the notice to a deleted account's address, which can't wait for the next tick, is sent straight away (`sendAccountDeletedNotice`).
- Actions that send email or can be guessed at (invitations, codes, links) are rate-limited with `assertRateLimit` (`src/server/rate-limit.ts`).
- Read configuration through `env` (`src/lib/env.ts`), never `process.env` (ESLint enforces it in `src/`). New environment variables go in `src/lib/env-schema.ts` and `.env.example`, and in the CI workflow or Playwright `webServer.env` if tests need them.
- Keep `server-only` out of `src/lib/auth.ts`, `src/db/` and the files they import: the Better Auth CLI (`pnpm auth:schema`) can't load them otherwise.

## Database

- IDs are always UUIDv7 generated by Postgres (`uuidv7()`), never auto-increment; every foreign key gets an index. The integration tests enforce both.
- Schema changes: edit `src/db/schema/`, run `pnpm db:generate`, commit the migration in `drizzle/`. After changing Better Auth's config, run `pnpm auth:schema` first. Don't hand-edit `src/db/schema/auth.ts`.
- Services take a `ServiceContext` and are covered by `*.int.test.ts` integration tests against the test database.
- Background work runs as a job in `src/server/jobs`, never in a request or a script of its own (decision 0018; the steps for adding a recurring or queued job are in `docs/jobs.md`). Every job is safe to run again, stops starting new work at its `deadline`, keeps each piece of work to seconds with a time limit on every network call (a run the platform stops at 60 seconds counts as failed), and keeps personal data out of its summary. A queued job is added with `queueJob` inside the change's transaction where there is one, its payload holds only IDs, small settings and references (never names, addresses or other personal data), and it returns `skipped` when what it was about is gone; code that queues jobs (`src/server/queue`) never imports the code that runs them.
- A module that outgrows one file (around 500 lines, or several jobs) becomes a folder whose `index.ts` is its public API: files inside import each other directly, code outside imports only the folder (add it to `FOLDER_MODULES` in `eslint.config.mjs`, which enforces this), and its tests sit next to its files with shared helpers in the folder's `test-helpers.ts`.
- New server and lib files go in the topic folder they belong to (`src/server/auth/`, `src/server/people/`, `src/lib/sign-in/`, `src/lib/tables/`, `src/lib/request/`, `src/lib/i18n/`, `src/lib/authz/`), with their tests next to them; code shared by every topic stays at the root of `src/server` or `src/lib`. Shared e2e helpers go in `e2e/support/`.
