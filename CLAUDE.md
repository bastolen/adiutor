## How to work on a request

- **Plan first, ask first, in plan mode.** Every task (anything that changes files, runs commands that change state, or takes several steps) goes through the actual plan mode: enter it (`EnterPlanMode`) if the session isn't in it already, investigate read-only, ask all your questions with the question tool, then present the plan with `ExitPlanMode` and change nothing until it's approved. Answers to your questions aren't the go-ahead; approving the plan is. This also applies to a task handed over by another session, and to a new task or a substantial change of plan halfway through; a small correction within an approved plan doesn't need it again. Subagents carry out a step of an approved plan and don't plan again. Small questions, explanations and read-only lookups get a direct answer, without plan mode. Sessions in this project start in plan mode (`.claude/settings.json`) for the same reason.
- **Delegate to cheaper models when it doesn't cost quality.** Hand self-contained subtasks to an agent on a cheaper model: Sonnet for most delegated work (running and reading tests, investigations, mechanical refactors), Haiku only for simple searches and lookups. Keep design, security and anything that needs this conversation's context on the current model: a better result matters more than a cheaper one.

## Product

- Adiutor is a shared service desk, a ticketing system where companies raise requests with the staff and work them through together by commenting, explaining, approving and reporting. Prepaid hours and billing will come later but aren't designed yet; don't mention them in the UI until they are.
- Wording: staff screens talk about "users", "companies" and "staff" (never "clients", "your team" or "organization"); screens for company users talk about "your company" or its name, and about "requests". "Client" is only the name of a company role (Admin, Client, Watcher). Marketing text speaks to companies. Staff have `user.platform_role` (see `src/lib/authz/roles.ts`), and the name users see and Adiutor's default language are the single `staff_settings` row. Invitations and invite links without a company are for staff.
- Until requests are built, don't add navigation or pages for features that don't exist; hint at them in descriptions and empty states instead.

## Documentation

- Document all code with JSDoc-style `/** ... */` comments. This includes TypeScript, config files and CSS.
- Every file starts with a `/** @file ... */` block saying what it is for. Every export, component, function, config option and theme token group gets its own `/** */` comment.
- When you change code, update its comments, the README and the matching page in `docs/` in the same change, so documentation never drifts from the code.
- `README.md` is about the product and the project (what Adiutor is, its features, the tech stack, the quick start, contributing, security reporting, the license). Developer detail lives in `docs/`, one page per topic, each listed in `docs/README.md` and the README's Documentation table; add new pages to both.
- A significant decision (architecture, the security model, process) gets a record in `docs/decisions/` (template and index in its `README.md`). Read the record before changing such a decision; a change gets a new record that supersedes the old one.

## Code style

- Follow the Airbnb style guide, with braces around every `if`, `else` and loop body (ESLint enforces it), and give every `eslint-disable` comment its reason (`-- why`). No `any` and no `!` (check the value, or use `defined()` / `firstRow()` from `src/lib/defined.ts`), and await or handle every promise. Run `pnpm lint:fix` and `pnpm format` after changes, then `pnpm lint`, `pnpm format:check`, `pnpm typecheck` and `pnpm test` must pass.
- Keep `.vscode/extensions.json` and `.vscode/settings.json` in sync with the tooling: when a linter, formatter or framework that has an official VS Code extension is added, removed or reconfigured, update both files (and the "Editor setup" section of `docs/code-style.md`). Keep the debug configurations in `.vscode/launch.json` and the tasks they start in `.vscode/tasks.json` working too: when a script, a test runner's entry point or the dev server's setup changes, update them and "Debugging in VS Code" in `docs/development.md`.
- The pre-commit hook (`.husky/pre-commit` → `lint-staged.config.mjs`) must cover every file type the linters and Prettier handle; update it when tooling changes.
- `pnpm audit` must stay clean (CI runs `pnpm audit --prod`). Fix a new advisory, or, when it can't be reached from the app, add it to `auditConfig.ignoreGhsas` in `pnpm-workspace.yaml` with a comment on why and when it goes away; remove the entry once its fix lands.
- In GitHub workflows, pin every action to a full commit SHA with a `# vX.Y.Z` comment and container images to a digest (Dependabot updates actions, Renovate npm packages and images), and give each workflow the least permissions it needs (`permissions: {}` or read-only at the top).
- Add or update tests with every change: Vitest `*.test.ts(x)` files next to the code in `src/`, Playwright specs in `e2e/`. Tests cover the application only: no tests for config, tooling, scripts or the test helpers in `tests/`.

## UI and accessibility

- The UI must feel premium and trustworthy: calm, consistent, polished in every state. Build it from `src/components/ui/` and extend those components rather than styling one-off elements.
- Target WCAG 2.2 AA. Use the semantic colour tokens from `src/styles/theme.css` (`surface`, `foreground`, `muted-foreground`, `primary`, `danger`, ...); never lighten text with opacity (ESLint enforces it in `src/app` and `src/components`), and check contrast for any new token in both modes.
- Menus, selects and dialogs use Radix UI (via the wrappers in `src/components/ui/`). Destructive actions go through `ConfirmDialog`, never `window.confirm`.
- Everything must work with the keyboard alone: visible focus (`focusRing`), logical tab order, Escape closes the open layer and focus returns to its trigger. When an action removes the control that had focus (a removed row, a swapped button, a dismissed notice), focus moves to its card's heading or the main content (`restoreFocusIfLost` in `src/components/ui/focus-fallback.ts`), never `<body>`. Icon-only buttons need an `aria-label`; decorative icons get `aria-hidden`.
- Give a `Card` an `id` (a section ID, `isSectionId`) when a control in it can send the user away and back (a confirmation, a provider, an emailed link), so they come back to that card: return addresses keep the page, its tables (`PageUrl.current()`) and the card's anchor (`ReturnToField`, `useRecentConfirmation`, `confirmChangeUrlFor`). Never build a return address by string concatenation without encoding it.
- Pages stay alive across navigation (Cache Components keeps them in React `<Activity>`), so forms use `useTransientActionState` (and pass its `onSubmit` with the action, so a refused submit keeps the input; a form that edits a saved setting passes `resetOnSuccess: false`, or a select would jump back to the value from before the save), and status messages and dialog open state use `useTransientState` (`src/components/ui/use-transient-state.ts`): an error message or an open dialog must not still be there when the user comes back. ESLint refuses `useActionState` outside that file.
- Ship only the code a page needs to the browser. Client components never import zod or `@/lib/validation` (shared limits live in `@/lib/input-rules`), pages outside the sign-in pages load the auth client with `loadAuthClient()` when an action needs it, and other libraries needed only for an action are loaded with `import()` when it happens (like `qrcode`). `src/client-imports.test.ts` enforces this; add new heavy libraries to its rules.
- The Content Security Policy only runs scripts with the request's nonce (`src/lib/request/csp.ts`, set by `src/proxy.ts`): never add inline scripts or `on…=` attributes; an unavoidable inline `<script>` takes the nonce from `(await headers()).get(NONCE_HEADER)`. Specs import `test`/`expect` from `e2e/support/test.ts`, which fails on CSP violations the pages report (ESLint enforces it). Keep the proxy matcher (`src/proxy.ts`) from skipping paths by extension: only real static files may skip it.
- Every control needs hover, focus-visible, disabled and busy states and the right cursor (pointer on clickable things, not-allowed when disabled). Forms use visible labels and `autocomplete`. In the signed-in app, every success is a toast and every error is shown inline with `Alert` and as a toast (`useToast` in `src/components/ui/toast.tsx`; `RowAction`, `ActionDialog`, `RoleSelect`, `ResultAlert` and `Alert`'s `alsoToast` do it for you). The signed-out pages show results inline only.
- Tables of records sort and paginate: define each table in `src/lib/tables/tables.ts` (a page's main table has no prefix; every other table on the page gets its own), read its state with `parseTableState`, build its links with `createPageUrl` (from known parameters only, never by copying the URL) and render `SortMenu` (the only way to sort: headers are plain `Th`s with `aria-sort={table.ariaSort(...)}`) and `Pagination` in the card footer (with `showsPagination`). The content stops growing at 1280px, so pick columns that fit 942px there and move the rest under the name; long names and addresses get `wrap-anywhere`. List services take `Partial<TableState>`, resolve it with `resolveTableState` and return `Paged<T>` (via `paginate` in `src/server/pagination.ts`), ending every sort with the row's ID. Pagination e2e tests use only the seeded "Adiutor Tests Paging" company.
- Every page must pass `e2e/a11y.spec.ts` (axe, light and dark) and new interactive patterns get a check in `e2e/keyboard.spec.ts`. Add new pages to `a11y.spec.ts`.

## Languages

- Every text people see or hear (JSX text, `aria-label`, `title`, placeholders, toasts, errors, page titles, emails) is a message in the catalogues `src/messages/<locale>/<area>.json`, added to every language in the same change: en-US is the source, nl-NL and es-ES follow the translation rules in `docs/i18n.md` (informal je and tú, "Adiutor" never translated). `pnpm lint:messages` checks they're complete; ESLint refuses hard-coded text in JSX and text props (`src/app`, `src/components`, `src/emails`).
- One message is one whole sentence with named ICU arguments, so each language chooses its word order: never glue translations together (`+`, template literals) or pass a piece of a sentence as an argument. Plurals wrap the whole sentence; links inside a sentence are `t.rich` tags.
- The language is the person's own (the `adiutor.locale` cookie, mirroring their account), else Adiutor's default (`staff_settings.default_locale`), else, before setup only, the browser's `Accept-Language`: use `requestLocale()` or `localeFromHeaders()`, never your own parsing. Language choices name each language in itself with its flag (`LANGUAGE_OPTIONS`, `LanguageFlag`).
- Server Components, actions and metadata translate with `useTranslations` / `getTranslations`. Client components get messages from the root provider (`common`) or `ClientMessages` (the page's own namespaces, inside its `<Suspense>`). Code outside React or a Next.js request (emails, services, jobs, scripts) uses `translator(locale, namespace)` with the locale it's given; keep `next-intl/server` out of `src/server/`.
- Text in a route's static shell (outside its `<Suspense>`) comes from a client component that reads the root provider, so Partial Prefetching can prefetch the shell.
- Format dates with `src/lib/format.ts` and the reader's locale (times are UTC); numbers are ICU `{n, number}` arguments in the message. A cached function never reads the request's language: pass the locale in.

## Email

- Every email is a React Email template in `src/emails/` built with `EmailLayout` and the blocks in `src/components/email/` (inline styles from `theme.ts`, no CSS variables). Never send hand-written strings.
- Each template's props extend `EmailBaseProps` and its exported `PreviewProps` start with `...PREVIEW_BASE` (both in `src/emails/base-props.ts`: the app URL `https://adiutor.dev`, `logoSrc: '/static/logo.png'` and `locale: 'en-US'`), followed by Adiutor example data. Each template translates with `translator(locale, 'emails.<name>')` and is written in the recipient's language (`recipientLocale`: their saved `user.locale`, else Adiutor's default language for someone on Default, never the sender's, else en-US; an invitation's `invitation.locale`; see `docs/email.md`). Each template also exports a builder that renders it with `renderEmail`, has a footer `reason`, and is covered in `src/emails/emails.test.tsx` in every language (subject, links, plain text). The main link must be the first link in the plain text.
- Images are linked from the app's public URL, never attached. Templates loaded by `src/lib/auth.ts` are imported inside the send callbacks, so loading the auth config never loads React.

## Dark mode

- Every UI change must work in light and dark mode. Use the semantic colours instead of fixed ones like `white` or `ink` (ESLint enforces it in `src/app` and `src/components`; a deliberate exception gets an `eslint-disable` with its reason), and the `dark:` variant for anything else.
- Never read the theme on the server (cookies would make every page dynamic); it is applied by the inline `themeScript` in the root layout.

## Authentication and permissions

- Every permission check goes through `src/lib/authz` (pure rules) and `src/server` (services check permissions themselves; pages use `src/server/authz.ts`). Never compare roles inline in pages or components (ESLint catches a role compared with a string).
- MFA rules live in `src/lib/authz/mfa/`; they take the user's MFA role (`mfaRoleOf`: staff Admins and Managers, or the Admin of an active company, require MFA), never the staff role alone. `getActor()` sends users whose role requires MFA to the Security page until they have it; only the account pages and the navigation may pass `allowMissingMfa: true`.
- Account existence (whether an email has an account or is a member) may only be shown to staff, via `mayRevealAccountExistence`. Company users' and signed-out screens must give identical responses.
- Never show users the IP address or browser of someone else (an admin who acted on their account, whoever typed a wrong password for their address), on screens or in emails: only staff with `audit:view` see those, in the audit log.
- Pages are protected by default by `src/proxy.ts`; only add a path to `PUBLIC_PATHS` when it must be reachable signed out. The proxy is never the security check.
- Read the signed-in user with `getActor()` / `requireCompanyAccess()` inside a `<Suspense>` boundary (Cache Components).
- Only `src/lib/authz/mfa/` decides MFA rules (who needs it, what counts, which sign-ins had a second step); don't re-implement them elsewhere. Load a user's MFA facts with `loadMfaStates` / `loadMfaContext` (`src/server/auth/mfa-state.ts`), which leave out provider accounts linked at sign-in that the user hasn't confirmed (`account.confirmed`), and decide whether a session counts when it's read (`isSessionMfaVerified` with the current MFA role), never from `session.mfa_verified` alone.
- OAuth providers are declared once in `src/lib/sign-in/oauth-providers.ts` (`OAUTH_PROVIDERS`, `MFA_PROVIDERS` for those that can prove MFA, and `PROVIDER_ACCOUNT_NAME_CLAIMS` for how their accounts are named, e.g. GitHub's username), with their credentials in `src/lib/sign-in/providers.ts`, their icon in `PROVIDER_ICONS` and their MFA check in `src/server/auth/provider-mfa.ts`. Never compare provider IDs such as `'github'` inline (ESLint flags them outside the files above): use `isMfaProvider`, the configured lists (`availableProviders`, `signInProviders`) and `PROVIDER_LABELS` (the file comment lists what a new provider needs).
- A provider account's name (`account.accountName`) is noted from the provider's profile in Better Auth's `user.validateUserInfo` and stored by the account hooks of the same request (`noteProviderAccountName`). That hook must never refuse anyone: Better Auth refuses the sign-in when it throws or returns an error. Account names are personal data: only for display (match accounts by `accountId`), never logged, shown to the user themself and, on the user's page, only to staff Admins (`users:manage`).
- Sessions last a fixed 7 days (`disableSessionRefresh` in `src/lib/auth.ts`). Don't turn session refresh back on without refreshing the cookie where cookies can be set (a Route Handler, a server action or the proxy): pages render where they can't, so the database row would outlive the cookie.
- Signing out removes every cookie the browser sends except the "Last used" sign-in method and the language (`cookiesToClearAtSignOut` in `src/lib/sign-in/auth-cookies.ts`), so the next person on the browser starts clean: set new cookies with `path: '/'` so sign-out reaches them, and key anything a user leaves in `localStorage` to that user, or better, save it with their account.
- Changes that would leave a role that requires MFA without it are refused in the guards, the services and the Security page through one rule (`wouldRemoveRequiredMfa`); add new sign-in changes to it (and to `signInChangeOf` for Better Auth endpoints). One sign-in change per user at a time: the guards take the lock for those endpoints, the OAuth callback decides whether a provider counts under it (`holdSignInChangeLock`), and services that change sign-in methods themselves run inside `withSignInChangeLock` (`src/server/auth/sign-in-change-lock.ts`), reading the MFA state only once they hold it. Better Auth's server-only endpoints (e.g. `setPassword`) have no path, so the guards never see them: call them through a service that applies the rules (`setFirstPassword`).
- Changes that can make a user's role require MFA (staff or company roles, memberships, joining, reactivating a company) run inside `withMfaPromotion` (`src/server/auth/mfa-promotion.ts`) in their transaction, so the user's sessions without a strong factor end.
- Email codes are never accepted once an authenticator app is set up, and never count for roles that require MFA (`allowsEmailCodes`). Changing sign-in methods (passkeys, linked accounts, two-step verification, backup codes, a first password) needs a confirmation with the second step from the last 15 minutes (`mfaConfirmedUntil`) once the account has MFA or any other second step (`canConfirmSessions`); `src/server/auth/auth-guards/` enforces this for Better Auth's endpoints too, and server actions and services check `needsRecentConfirmation(actor)`. The guards' refusal codes are declared once in `src/lib/sign-in/sign-in-refusals.ts`, with their messages in `auth.codes`; forms turn an error into text with `authErrorText`, which shows only the refusals in `SERVER_WORDED_CODES` as the server words them (never Better Auth's English). On the Security page, use `useRecentConfirmation` so starting such a change sends the user to the step-up page first.
- Only the Better Auth endpoints the browser uses are open over HTTP (`src/lib/sign-in/auth-endpoints.ts`); when the browser needs another one, move it from `DISABLED_AUTH_PATHS` to `BROWSER_AUTH_PATHS` deliberately.
- Better Auth's errors land on `/sign-in-error` (`onAPIError.errorURL`), which explains them without the code and records a reference for admins with `recordSignInError` (`src/server/auth/sign-in-errors.ts`): the log line holds only the reference and code, and the `sign_in_error` row (kept 7 days) adds Better Auth's description and the user ID. Add a message (`auth.codes`) and its code (`src/app/sign-in-error/messages.ts`) for new codes users can hit.
- Server code never logs personal data or secrets itself (addresses, names, tokens, request bodies): log what failed, with an ID where needed. Logs drop database values through `installLogRedaction` (`src/lib/log-redaction.ts`, installed in `src/instrumentation.ts`); new scripts call it first (they may still tell the operator what they did, e.g. which address they signed out). The one exception is the development email fallback in `src/lib/email.ts`, which prints whole emails when there's no SMTP server and never runs in production.
- Read the client's IP with `requestInfoFromHeaders` and `ipAddressOptions` (the same resolution Better Auth uses); never parse `X-Forwarded-For` yourself.
- Read the session token from a request only through its signed cookie (`getSignedCookie` with Better Auth's secret, see `signedSessionToken`), never by parsing the cookie: a token from the database must not pass for a session. Don't keep OAuth tokens beyond the request that needs them (`withoutKeptTokens`).
- When someone loses the right to manage a company or the staff (role change, removal, deactivation, deletion), revoke what they sent with `revokeInvitesWithoutManager`.
- Giving someone a lasting way in needs the giver's confirmation with their second step from the last 15 minutes, like changing sign-in methods: any staff role (or a higher one) and a company's Admin role, by invitation, invite link, role change, adding a member or registering a company (`grantNeedsConfirmation` in `src/lib/authz/guards.ts`). Services enforce it with `assertConfirmedForGrant` (code `confirmation_required`), actions wrap the service call in `confirmFirstIfNeeded` (to the step-up page and back), and forms ask before anything is typed (`useConfirmBeforeGrant`, `ConfirmFirstNote`, `RoleSelect`'s `target`, `ActionDialog`'s `confirmFirst`). Becoming a staff Admin emails the other staff Admins (`notifyStaffAdminAdded`).
- Nobody raises their own staff role (`isStaffRoleRaise`); they may only step down. Finance and Support can't use invite links (`mayUseInviteLinks`), directly or through the invitation a link sends; check it before a link is used up.
- New permission-relevant services get a row in `src/server/authorization-matrix.int.test.ts`.
- Every security-relevant change (sign-in methods, sessions, roles, accounts, invitations) calls `recordEvent` from `src/server/audit.ts`, in the change's transaction where there is one. Changes the user should know about also send a security notice (`sendSecurityNotice`); it names the device and IP address only with `showDevice: true`, which is for changes the user made themselves.
- Actions that send email or can be guessed at (invitations, codes, links) are rate-limited with `assertRateLimit` (`src/server/rate-limit.ts`).
- Read configuration through `env` (`src/lib/env.ts`), never `process.env` (ESLint enforces it in `src/`). New environment variables go in `src/lib/env-schema.ts` and `.env.example`, and in the CI workflow or Playwright `webServer.env` if tests need them.
- Keep `server-only` out of `src/lib/auth.ts`, `src/db/` and the files they import: the Better Auth CLI (`pnpm auth:schema`) can't load them otherwise.

## Database

- IDs are always UUIDv7 generated by Postgres (`uuidv7()`), never auto-increment; every foreign key gets an index. The integration tests enforce both.
- Schema changes: edit `src/db/schema/`, run `pnpm db:generate`, commit the migration in `drizzle/`. After changing Better Auth's config, run `pnpm auth:schema` first. Don't hand-edit `src/db/schema/auth.ts`.
- Services take a `ServiceContext` and are covered by `*.int.test.ts` integration tests against the test database.
- A module that outgrows one file (around 500 lines, or several jobs) becomes a folder whose `index.ts` is its public API: files inside import each other directly, code outside imports only the folder (add it to `FOLDER_MODULES` in `eslint.config.mjs`, which enforces this), and its tests sit next to its files with shared helpers in the folder's `test-helpers.ts`.
- New server and lib files go in the topic folder they belong to (`src/server/auth/`, `src/server/people/`, `src/lib/sign-in/`, `src/lib/tables/`, `src/lib/request/`, `src/lib/i18n/`, `src/lib/authz/`), with their tests next to them; code shared by every topic stays at the root of `src/server` or `src/lib`. Shared e2e helpers go in `e2e/support/`.
